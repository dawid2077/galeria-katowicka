Step 1: User Clicks the Button (Frontend)The user visits your web app and clicks "Sign in with Google."The browser communicates with Google's Identity JS SDK.A Google popup window or redirect appears, asking the user to choose their Google account.  Step 2: Google Asks for ConsentGoogle shows the account chooser and consent dialog:  Google asks: "Allow [Your Web App Name] to access your email and profile info?"If the user agrees, Google authenticates them on their end.Step 3: Google Returns an ID Token to FrontendOnce authenticated, Google closes the popup and hands your frontend a cryptographically signed ID Token (a JWT credential).  This token contains verified information directly signed by Google:sub: Google's immutable unique User ID (e.g., "109283746501928").email: user@gmail.comemail_verified: truename: "Jane Doe"picture: "[https://lh3.googleusercontent.com/](https://lh3.googleusercontent.com/)..."Step 4: Frontend Sends Token to FastAPIYour frontend immediately takes that ID token and sends it over an API request (e.g., POST /auth/google) to your FastAPI backend:JSON{
  "id_token": "eyJhbGciOiJSUzI1NiIsImtpZCI6..."
}
Step 5: FastAPI Verifies the TokenFastAPI uses Google's official Python library (google-auth) to verify the token.FastAPI checks:Is the cryptographic signature valid (did it actually come from Google)?Has the token expired?Was this token issued specifically for your Google Client ID?Step 6: The Database Check ("Sign Up" vs. "Sign In" Magic)Once verified, FastAPI extracts the user's google_id (the sub field) and email. Your code queries your database:  SQLSELECT * FROM users WHERE google_id = '109283746501928';
Here is how Sign Up vs. Sign In is determined automatically:Scenario A: Sign Up (User is NEW)The database query returns None (no matching user exists).FastAPI automatically runs an INSERT:SQLINSERT INTO users (google_id, email, full_name, profile_pic) 
VALUES ('109283746501928', 'user@gmail.com', 'Jane Doe', 'https://...');
Result: The account is created instantly without the user ever picking a password.Scenario B: Sign In (User ALREADY EXISTS)The database query finds an existing user record matching google_id.FastAPI skips the insert step and retrieves the existing user_id.Result: The user is recognized and logged into their existing account.Step 7: FastAPI Establishes User PersistenceNow that FastAPI knows who the user is (whether newly created or existing):FastAPI generates a secure session token or cookie (like an HttpOnly JWT cookie).FastAPI sends the HTTP response back to the browser along with the Set-Cookie header.Step 8: Subsequent RequestsThe browser stores that HttpOnly cookie. Every time the user opens a new page or makes an API call to FastAPI, the browser automatically attaches the cookie.FastAPI checks the cookie, sees the user is logged in, and serves their data—maintaining persistence.
